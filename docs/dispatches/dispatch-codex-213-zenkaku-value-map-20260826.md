## 1. 何を作るか（画面の言葉で）

1. **表記のちがいを自動でそろえる**: FMの「新規」とKintoneの「新設　新規」のように、同じ意味なのに
   書き方が違う値が26のドロップダウン項目にありうる。いまは書き方が完全一致する案件しか通らない。
   変換表で自動でそろえ、それでも合わない値は「どの項目のどの値が合わないか」を画面で分かる言葉で伝える。
2. **住所のカタカナが壊れるのを直す**: 「ガーデンハイツ」が「ガ-デンハイツ」になってしまう
   （長音「ー」をハイフンに変えすぎている）。カタカナの長音はそのまま、数字の間だけハイフンにする。
3. **チーム選択を画面にする**: チーム名から担当が2つ以上見つかったとき、いまはブラウザの簡易入力窓
   （番号を打たせる window.prompt）。画面上でボタンで選べるようにする。

## 2. ①FM→Kintone表記変換表

- 対象は `dropdown-crossref.txt` の取次連携用26項目（＝FM値をそのまま入れているドロップダウン）。
  対応するFM列名は `scripts/zenkaku-agent/config.example.json` の fieldMap を正とする
  （例: Kintone「携帯キャリア」← FM「携帯キャリア営業用」）。
- **変換表は1ファイルに分離**（例: `src/app/system/mypage/_lib/zenkaku-value-map.ts`）。
  形式は「Kintone項目名 →（FM値 → Kintone選択肢値）」の素直なデータで、
  **後から Claude が行を足すだけで効く**こと（ロジックに触らず表だけ育てられる形）。
- 適用場所は `zenkaku-submit.ts` の `buildKintoneRecords` 側（サーバ）。ホスト常駐ブリッジ
  （`scripts/zenkaku-agent/`）と fieldMap は**今回は変更しない**（FM列の追加なし）。
- 初期エントリとして確定しているのは1件: **工事種別「新規」→「新設　新規」**（テストデータで実際に発生した表記）。
  現データの実測では他の表記ズレは見つかっていない（probe-vs-options.txt 参照）ため、残りは空でよい。
  表に「実測2026-08-26時点で他のズレなし・見つかり次第ここに足す」と1行コメント。
- 変換の規則:
  - 完全一致で引く（前後の空白はトリム）。表に無い値はそのまま通す
  - 空欄は空欄のまま（変換・補完しない）
- **変換後も選択肢に無い値**が残ったときの扱い: 投入前に fields234.json 由来の選択肢一覧と突合して
  止め、画面に「工事種別『××』は取次側の選択肢にありません。管理者へ連絡してください」の形式で
  項目名と値を出すことを推奨（開発者用語なし）。別方式（Kintoneエラー本文の翻訳など）にするなら
  理由を完了報告に書く。選択肢一覧の持ち方（スナップショット同梱か、ビルド時生成か）はCodex提案。

## 3. ②住所の長音（halfWidthAddress の修正）

- 現状: `src/app/system/mypage/_lib/zenkaku-submit.ts` 8行目
  `replace(/[‐‑‒–—―ー−]/g, "-")` が **カタカナ長音「ー」(U+30FC) まで**ハイフンにしている。
- 直し方:
  - 「ー」を常時変換の文字クラスから**外す**
  - そのうえで**数字と数字の間の「ー」だけ**は「-」にする（例: `1ー2ー3` → `1-2-3`）。
    NFKC正規化が先に走るので全角数字は半角になってから判定してよい
  - `ガーデンハイツ` → `ガーデンハイツ`（不変）を必ずテストに入れる
- `zenkaku-submit.test.ts` の既存テストを実態に合わせて更新。
