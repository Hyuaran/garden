# Codex-216 マイページ届出モーダル（提出・登録の本物化＋届出受信箱＋Kintoneつなぎ反映）

- 発行日: 2026-08-26
- 対象: マイページ「提出・登録情報」カード（/system/mypage）＋ Root の新画面「届出受信箱」
- 作業ツリー: `C:\garden\a-bloom-008`（**Codex-215 マージ後の main** から feature ブランチで）
- 背景（東海林さん確定・2026-08-26）:
  - いまは「じぶんフォーム」で従業員が提出→事務が Kintone 従業員名簿へ手動転記（転記忘れあり）。
    このモーダルが**じぶんフォームを置き換え**、Garden（Root）が正本になる
  - ただし **Garden 全体実装は約1年後**で、現場はそれまで Kintone を使う。
    → **つなぎとして、確定時に Kintone へ自動反映する（案1・決定）**：既存アプリにレコード追加＋名簿の該当項目更新。
    解約時に捨てられる薄い作りにする
  - 交通費の申告は「**従業員は駅を入力するだけ**→事務が最安経路の金額を調べて提案→**本人が承諾して確定**」の流れ

## 1. 何を作るか（画面の言葉で）

1. マイページの「提出・登録情報」の各ボタンを押すと**モーダルが開き、その場で送信できる**。
   種類は5つ（**「給与受取口座の変更」を新たに追加**する）:
   緊急連絡先変更／通勤経路変更／給与受取口座の変更／退職届／秘密保持誓約書
2. 送信すると「受け付けました。事務から連絡します」と出て、事務は Root の新画面**「届出受信箱」**で
   確認・対応できる
3. 交通費（通勤経路変更）だけは往復がある: 受付→事務が金額を入れて提案→**マイページに
   「日額◯◯円（片道◯◯円）で申請します。よろしいですか？」が出る→本人が承諾→確定**

## 2. フォーム5種の項目

- **緊急連絡先変更**: 氏名／続柄／電話番号／住所（任意）
- **通勤経路変更**: 新しい最寄り駅（自由入力）／適用希望日／補足（任意）。**金額は入力させない**
- **給与受取口座の変更**: 銀行名／金融機関コード／支店名／支店コード／種別（普通固定でよい）／口座番号／口座名義カナ
  （Kintone「口座一覧」app92 と同じ構成。入力欄には数字桁のガイドを出す）
- **退職届**: 退職希望日／理由（任意）／送信前に「送信後、事務から連絡します」の注意書き
- **秘密保持誓約書**: 誓約文の表示＋「内容に同意します」チェック＋氏名の入力（＝電子署名扱い・送信日時を記録）

## 3. 状態の流れ

- 共通: **受付済み → 対応中 → 完了**（受信箱で事務が進める。差し戻し＝「対応中」でコメントを本人に見せる形は不要・今回なし）
- 通勤経路変更のみ: **受付済み → 金額提案中 → 本人承諾待ち → 確定**
  - 受信箱で事務が「片道金額」を入力して提案 → 本人のマイページに承諾カードが出る（日額=片道×2 を明記）
  - 本人が［この金額でお願いする］→ 確定。［取りやめる］も可（状態=取り下げ）

  - `submission_type text`／`payload jsonb`／`status text`／`proposed_one_way integer`（交通費の提案片道・円）
  - `handled_by`／`handled_at`／`created_at`／`updated_at`（既存 `root_update_updated_at()` トリガー）

  - 交通費確定: `root_employees.commute_daily_allowance = 片道×2`（上限は変更しない）

## 5. Kintone つなぎ反映（確定時・案1）

- **交通費確定** → ①「交通費一覧」（app93）へレコード追加（KOTID・従業員名_姓名・交通費　片道・交通費上限・通勤経路）
  ②「従業員名簿」（app56）の該当従業員の `交通費_片道`・`交通費上限` を更新
- **口座確定** → ①「口座一覧」（app92）へレコード追加（支払先=氏名・従業員名_姓名・KOTID・銀行名・金融機関コード・
  支店名・支店コード・種別・口座番号・口座名義カナ・支払用途=給料賃金・稼働状況=○）
  ②「従業員名簿」（app56）の口座項目（スロット1: `銀行名_1`・`金融機関コード_1`・`支店コード_1`・`口座番号_1`）を更新。
  スロット1/2 の使い分けが名簿の実データから読み取れない場合は**スロット1更新を既定**とし、完了報告に明記
- 緊急連絡先・退職届・誓約書は **Kintone 反映なし**（Root 保存のみ）
- 突合キーは **KOTID = root_employees.kot_employee_id**。KOT の無い従業員（役員・外注）は名簿更新をスキップし受信箱に注記
- 実装の作法:
  - トークン・アプリIDは環境変数（名前は Codex が決めて完了報告に書く。値は Claude が設定。**未設定時は反映をスキップ**し
    受信箱の該当届出に「Kintone未反映」を表示）
  - Kintone 反映が失敗しても**届出の確定自体は成功**とし、受信箱に「Kintone反映失敗（再実行）」ボタンを出す
  - レコード追加・更新は既存の前確投入と同じ流儀（`X-Cybozu-API-Token`、更新は
    `X-HTTP-Method-Override` 不要の PUT 系 API、エラーは応答本文までログ）
  - 解約時に丸ごと外せるよう、Kintone 反映は1モジュールに分離する

## 6. 届出受信箱（Root の新画面）

- 場所は Root 配下（例 `/root/inbox`）。閲覧できるのは manager / admin / super_admin
- 一覧（新しい順・種類と状態で絞り込み）→ 行を開くと内容全文＋状態操作
- 通勤経路変更には「片道金額」入力＋［この金額で提案する］
- 見た目は Root の既存画面の流儀に合わせる。文言は業務の言葉（開発者用語なし）

## 8. テスト

- 5種それぞれ: 送信→受付表示→受信箱に出る→状態遷移
- 交通費: 駅だけで送信できる（金額欄が無い）→提案→本人承諾カード→確定で日額が片道×2 に更新／取り下げ
- 口座確定: bud_employee_bank_accounts の旧行が is_active=false になり新行が active

- KOT 無し従業員の名簿更新スキップ
- 権限: 一般従業員が受信箱を開けない

## 10.【差し戻し 2026-08-26・Claudeレビュー】Kintone連携のフィールド指定を実コードに修正

実装・API設計・受信箱・状態遷移は良い。ただし `submission-kintone.server.ts` が **Kintone のフィールドを
「ラベル」で指定しており、実フィールドコードと違うため、トークン設定後の実行で全部
GAIA_IQ11（指定フィールドなし）になる**（Codex-210系で踏んだのと同じ落とし穴。実コードはスナップショット
`C:\garden\_shared\attachments\mypage\fields56/92/93*.json` で実測済み）。以下に修正すること。

1. **交通費一覧（app93）へのレコード追加**の実コード:
   - KOTID → `ルックアップ`／従業員名_姓名 → `文字列__1行_`／交通費　片道 → `数値`／
     交通費上限 → `数値_0`／通勤経路 → `文字列__1行__1`
   ※「ルックアップ」という名前だがルックアップ設定は無いただのテキスト欄（トークン併記は不要・実測済み）
2. **口座一覧（app92）へのレコード追加**の実コード:
   - KOTID → `ルックアップ_0`／従業員名_姓名 → `文字列__1行__0`／金融機関コード → `文字列__1行_`
   - 支払先・銀行名・支店名・支店コード・種別・口座番号・口座名義カナ・支払用途・稼働状況は コード=ラベルでそのまま可
3. **従業員名簿（app56）の更新は updateKey 不可**：`打刻ID` は重複禁止設定ではない（unique=false 実測）。
   - 方式変更: `X-HTTP-Method-Override: GET` で `打刻ID = "<KOTID>"` を検索 →
     **0件=スキップして kintone_note に記録／複数件=作成日時が最新の1件を採用** → `$id` 指定の PUT で更新
   - 更新フィールドコードは現行どおりでよい（交通費_片道・交通費上限・銀行名_1・金融機関コード_1・支店コード_1・口座番号_1 は実在確認済み）
4. テストのモック・検証も実コードに合わせて更新（ラベル表記が残っていないことをテストで担保）

## 11.【差し戻し2 2026-08-26・本番E2Eで発覚】ルックアップ実物への対応3点

マージ・本番デプロイ後の実E2Eで、交通費確定時の Kintone 反映が **GAIA_LO04** で失敗した。
原因は KOTID 項目（app93 `ルックアップ`／app92 `ルックアップ_0`）が**本物のルックアップ項目**だったこと
（fields.json は lookup:null を返すが、実挙動で確定。参照先は名簿56の打刻ID）。
Claudeが実POSTで検証済み: **参照先トークン併記＋実在KOTIDなら成功する**（app93 レコード483を作成できた）。
以下を `submission-kintone.server.ts` に修正すること。

1. **app92・app93 へのレコード追加は、X-Cybozu-API-Token に名簿56のトークンを併記**する
   （`${targetToken},${rosterToken}`。前確投入の #471 と同じ流儀）
2. **KOTID が名簿56の打刻IDに実在しない場合**（例: デモ垢）、92/93への追加は必ず GAIA_LO04 で失敗する。
   → 既にある名簿検索（56更新用）を**先に**実行し、0件なら **92/93への追加もスキップ**して
   注記「KOTIDが名簿に無いためKintone反映をスキップ」を kintone_note に記録する（失敗扱いにしない）
3. **失敗時の kintone_note に Kintone 応答本文（先頭200字程度）を含める**
   （現状の「Kintone反映失敗」だけでは受信箱で原因が分からない。前確 #468 の教訓）
4. テストを上記3点に合わせて更新（併記トークン・0件スキップ・エラー本文の記録）
