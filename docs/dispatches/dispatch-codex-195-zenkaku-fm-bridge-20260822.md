## 0. これは何をするものか

Codex-194 で、判定ルール（Gardenチェック）と画面はできた。ただし読むデータが**仮のもの**のまま。
今回は、**本物の FileMaker11 の営業マスタを読んで判定する**ところまでをつなぐ。

```
営業が［連携チェック］を押す
  → Garden（クラウド）が「この営業IDを見てほしい」という依頼を1件つくる
  → 社内ホストPCの常駐プログラムが数秒おきに依頼を取りに来る
  → ODBC で FileMaker の営業マスタを1件読む
  → Garden へ返す → Garden が判定して、画面に結果を出す
```

**なぜこの形か**：Garden はクラウド（Vercel）、FileMaker は社内LANにある。
**Garden から社内のFileMakerへは直接つなげない**ため、社内側から取りに来てもらう。
コール履歴の取込（`scripts/callcenter-agent/`）が同じ形で本番稼働しており、その土台を使う。

## 1. Garden側（クラウド）

### 1-1. 依頼を置く場所（Supabase）
`system_zenkaku_check_request`（新規）

| 列 | 内容 |
|---|---|
| `id` | 依頼ID |
| `sales_id` | 営業ID |
| `requested_by` | 依頼した社員（`auth.uid()`） |
| `status` | `pending` → `reading` → `done` / `failed` |
| `result` | 判定の結果（**指摘の一覧だけ**） |
| `error_code` | 失敗したときの区分（`not_found` / `fm_unreachable` / `timeout` 等） |
| `created_at` / `updated_at` | 時刻 |

**★営業マスタの中身（氏名・住所・電話番号など）はここに保存しないこと。**
受け取ったその場で判定し、**指摘の一覧だけ**を `result` に書いて、元のデータは捨てる。
（配信PDFと同じ考え方。個人情報を溜めない）

RLSは既存のやり方に合わせる。**依頼した本人と管理者だけが読める**こと。

### 1-2. API

| ルート | 誰が使うか | 役割 |
|---|---|---|
| `POST /api/system/zenkaku-check` | 画面（ログイン中の社員） | 営業IDを受け取り、依頼を1件つくって依頼IDを返す |
| `GET /api/system/zenkaku-check/[id]` | 画面 | 依頼の状態と結果を返す |
| `GET /api/system/zenkaku-agent/next` | 常駐プログラム | いちばん古い `pending` を1件取り、`reading` にして営業IDを返す |
| `POST /api/system/zenkaku-agent/result` | 常駐プログラム | 営業マスタ1件ぶんの値を受け取り、**その場で判定して** `result` に指摘だけ書く |

- 常駐プログラム用の2本は **Bearer 認証**（新しい環境変数 `ZENKAKU_AGENT_SECRET`）。
  コール履歴の `CALL_INGEST_SECRET` とは**別にする**（役目が違うため）。
- **ログにトークン・営業マスタの中身を出さないこと。**出してよいのは依頼ID・営業ID・状態・所要時間まで。
- 判定は Codex-194 の `evaluateGardenCheck` を**そのまま使う**（判定ロジックは触らない）。
- `reading` のまま**60秒**を超えた依頼は `failed`（`timeout`）にする。

### 1-3. 画面（`ZenkakuTab.tsx`）
- ［連携チェック］→ 依頼をつくる → **1秒おきに状態を見に行く**（最大30秒）→ 結果を出す。
- 待っている間は「社内のシステムに確認しています…」のような表示にする。
- 30秒たっても返らないとき、社内で読めなかったときの文言は**次に何をすればよいかを書く**。
  例：`社内のシステムに確認できませんでした。時間をおいて、もう一度お試しください。続くときは管理者へ問合せてください。`
  **開発者向けの言葉（timeout・ODBC・agent 等）を画面に出さないこと。**
- 営業IDがFileMakerに無かったときは `この営業IDは見つかりませんでした。番号をご確認ください。`

## 2. 社内ホストPC側（常駐プログラム）

`scripts/callcenter-agent/` と**同じ作法**で作る。既存のコール履歴の取込を**壊さないこと**。

- 置き場所は `scripts/zenkaku-agent/`（新規）。既存と同じく **32bit PowerShell 5.1**・ODBC DSNレス接続。
- 動き：**3秒おき**に `GET /api/system/zenkaku-agent/next` を叩く。依頼が無ければ何もしない。
  依頼があれば ODBC で営業マスタを1件読み、`POST /api/system/zenkaku-agent/result` で返す。
- 接続文字列の作り方・値の変換・ハング防止（親子プロセス）・ログの書き方は
  `CallCenterAgent.ps1` のやり方に合わせる。**同じ処理を書き写すのではなく、共通部分は Core を再利用**すること。
- タスク登録は既存と同じく **SYSTEM実行**（無ログイン・再起動でも動く）。
- 秘密（FMのパスワード・`ZENKAKU_AGENT_SECRET`）は**マシン環境変数**から読む。引数・ログに出さない。

### 2-1. ★確認できていないこと（勝手に決めない）
営業マスタは**コール履歴とは別のFileMakerファイル**。次の3つは実物を見ないと確定できない。

1. FileMaker の**データベース名**（コール履歴は `コール履歴`。営業マスタは不明）
2. **テーブル名**と、営業IDで1件引くときの**列名**
3. **判定に使う各項目の実際のフィールド名**
   （Excelの一覧は「FileMakerに接続できないためスクリーンショットから作成」と注記があり、実物と一致する保証がない）

→ **設定ファイル（`config.example.json`）で差し替えられる形にすること。**
   フィールド名の対応は **設定ファイルの表**にして、コードを直さずに直せるようにする。
   仮の値を入れておき、**READMEに「実物を見て直す手順」を書く**こと。
   **推測でフィールド名を決め打ちにしない。**

## 4. テスト

### Garden側
- 依頼をつくる → `pending` になる
- 常駐プログラム役が `next` を叩くと `reading` になり、同じ依頼が**二重に取られない**こと
- `result` を受けると判定が走り、**指摘だけ**が保存されること
  → **営業マスタの中身（氏名・住所・電話番号）がDBに残っていないこと**を明示的に確かめる
- `reading` のまま60秒超で `failed`（timeout）
- 認証：Bearerが無い／違うときは弾かれること
- 依頼した本人以外が結果を読めないこと
- 営業IDが見つからないときの返し方

### 常駐プログラム側
- ODBC の読み取りは**差し替え可能な形**にして、偽のデータで通ること（実機のFMには繋がない）
- 依頼が無いときは何もしない
- 読めなかったときは失敗として返し、**次の依頼へ進む**（止まらない）

### 画面
- 押してから結果が出るまでの表示が出ること
- 30秒で返らないときの文言が出ること
- §3のまとめ方になっていること（同じ見出しが繰り返されない）
